# 分页后端发布后的联合排查记录

这是合成生产故障材料，不能作为GPU性能实测。问题不归结为一个预先指定的根因，
也不要求围绕某个内部类重构；需要从离线证据、数值计算和持续状态分别建立假设并验证。

## 已有观察

采集端把CSV、JSONL和压缩导出放在同一目录。样本、重试、生产时钟和部署的身份列来自
不同源；文件顺序不是事件顺序。某次构建后画像样本数下降，另一版构建却使较新部署
提前进入候选集。控制面记录“ready”与服务真正可用的时刻是否相同，需要结合证据判断。

新后端的单分片值域没有溢出，但汇聚后的候选token有偏移。相同页会以多个逻辑位置
出现；query行及rank内head的排列也随导出变化。健康预览一致不足以证明推理结果一致。

正常输出第一段文字后，后续窗口可能才收到同名页的新版本。完整页、差分页和重传
可以描述同一内容，也可能互相矛盾。页分配日志、客户端前缀与最终计数并不总能互证。
应对比窗口中间的资源状态，而不是把所有异常都归为流终止处理。

发布时同一URL继续服务新旧请求，耗时样本来自不同接纳时刻。监控中的因子变化会影响
后续接纳；这些变化是否来自有效的新代反馈，需要追溯对应请求。最终页数归零不能
证明期间拒绝/接受的请求正确。

## 一个同时包含多方面问题的复现

`captures/paged-7/workload.json` 含多个build cutoff，原始数据先形成实际使用的部署与成本。
`p-staged` 在注册和就绪记录到达、发布记录尚未生效的间隙进入；其生成过程又跨过下一次
切换。活跃路径的测量包含同一样本的不同尝试，不能把原始输入问题当作旁路报表问题。
`p-coupled-held` 被接纳后发生发布切换，其旧流继续处理乱序query、逻辑别名和差分页。
两次 `p-coupled-probe-*` 在不同窗口阶段到达；旧流取消后第三次探测检查能否恢复。
另有 `p-held` 与 `p-probe-*` 检查正常完成后的恢复。生成内容、派发身份、页占用、
拒绝原因与反馈必须共同解释这些事件，不应由各模块分别编造一套状态。

依赖关系为：

```text
多源测量/时钟/发布记录 → 画像成本 + 部署资产
                              ↓
                         路由与接纳
                              ↓
                    KV / query 解释与注意力
                              ↓
                    采样结果 + 版本缓存
                              ↓
                 占用、释放和耗时反馈 → 后续接纳
                              ↓
                      监控与replay核对
```

每个箭头都可由公开数据、实际HTTP派发和连续checkpoint检查。一次局部修复可能让下游
原先被早期错误遮挡的偏差出现；不把“公开测试首次通过”当作全部故障已排除。

所有验收所需条件在题面引用的七份公开契约中；本记录提供观察和数据入口，不新增
隐藏规则。允许更换内核、缓存容器和模块布局，测试不调用私有helper或固定journal。
